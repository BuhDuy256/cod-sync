## What the product is

### I-1 · multi-shop COD reconciler

- **Statement:** The product is a web-hosted system, with accounts, that reconciles cash-on-delivery money for a shop sending parcels through two or more carriers.
- **Status:** confirmed
- **Spec implications:** Every use case assumes an authenticated account and a shop that owns its own data. The multi-carrier case is primary; a single-carrier flow is a subset of it.

### I-2 · reconciliation is the core

- **Statement:** Reconciliation is the product. Order records, waybills, status tracking, and return confirmation exist to feed reconciliation, not as the product's own purpose.
- **Status:** confirmed
- **Spec implications:** A foundation capability (order, waybill, status, return) is specified only as far as reconciliation needs it. A use case that does not end in a reconciliation outcome states why it exists.

### I-3 · one view of money across carriers

- **Statement:** The product gives one view of COD money spread across several carriers, each with its own schedule, file format, and fee naming.
- **Status:** confirmed
- **Spec implications:** Carrier differences in schedule, file format, and fee naming are normalized inside the product. No use case treats a carrier-specific format as the system of record.

### I-4 · the ledger is core, custody is a simulated extension

- **Statement:** A double-entry ledger of what each carrier owes, has paid, and still holds is part of the core. Holding a shop's money and releasing it — the wallet — is a simulated extension built on that ledger.
- **Status:** confirmed
- **Spec implications:** The core reconciles from money movements it reads, not ones it controls. No core use case requires the product to hold or release money. The wallet extension reuses the core ledger and does not add a second money model.

## Why it exists

### W-1 · money is opaque across carriers

- **Statement:** I believe a shop using several carriers cannot tell where its COD money is, how much each carrier holds, or which lumped bank transfer belongs to which order.
- **Status:** confirmed
- **Evidence:** [assumed]
- **Spec implications:** The product shows, per shop, how much money each carrier holds, and links each bank transfer to the orders it settles.

### W-2 · discrepancies are found too late

- **Statement:** I believe a shop finds money discrepancies only at period close, reconciling by hand, and misses carrier complaint deadlines.
- **Status:** confirmed
- **Evidence:** [assumed]
- **Spec implications:** The product flags a discrepancy when it arises, not at period close, and tracks each carrier's complaint deadline.

### W-3 · the value is money the shop can trust

- **Statement:** The product aims to let a shop know at any time where its money is, whether it has all arrived, what is wrong, and why, with evidence ready before a complaint deadline.
- **Status:** confirmed
- **Evidence:** [assumed]
- **Spec implications:** A reconciliation outcome names the discrepancy and its reason, and keeps the evidence needed to raise a complaint.

## Principles

### P-1 · the core runs without AI

- **Statement:** With AI turned off, the product still reconciles. AI only reads files in unfamiliar formats and explains in words why an order is off.
- **Status:** confirmed
- **Why:** AI is assistive, so it must not become a dependency of the money core.
- **Spec implications:** No reconciliation outcome depends on an AI result. An AI explanation is added to a result the core already produced.

### P-2 · no core capability depends on an external system

- **Statement:** No core capability requires a real external carrier or bank. A real API is used only where it is free and self-registerable; everything else is reached the same way through a simulated counterpart.
- **Status:** confirmed
- **Why:** The product must run and be measured without waiting on a partner.
- **Spec implications:** The core reaches a carrier or bank through one contract that a real or a simulated counterpart both satisfy. A use case never assumes a specific live provider.

### P-3 · the data generator is kept apart from the engine

- **Statement:** The part that creates test data with planted errors is kept apart from the part that detects them, and the detector is not told which errors were planted.
- **Status:** confirmed
- **Why:** So detection accuracy stays honest and is not the engine grading itself.
- **Spec implications:** Accuracy is measured against the generator's answer key, which the engine never reads.

### P-4 · money is governed by invariants

- **Statement:** The product holds money invariants that stay true regardless of the input [BR-?: COD money invariant].
- **Status:** confirmed
- **Why:** A broken invariant is a money error, so it is caught at the source rather than at period close.
- **Spec implications:** Every money-changing use case preserves the stated invariants. A state that breaks one is rejected, not stored.

### P-5 · a repeated or reordered event does not create money

- **Statement:** A duplicate or out-of-order carrier event does not create duplicate money [NFR-?: money result independent of event count and order].
- **Status:** confirmed
- **Why:** Carrier events arrive unreliably, so the money result must not depend on their count or order.
- **Spec implications:** Event intake is idempotent and order-independent. The same event applied twice yields the same money state.

### P-6 · accuracy is reported per discrepancy type

- **Statement:** Detection accuracy is reported for each discrepancy type, not as one aggregate number [NFR-?: detection rate per discrepancy type].
- **Status:** confirmed
- **Why:** An aggregate hides which errors the product misses.
- **Spec implications:** Each discrepancy type in the catalog carries its own detection-rate target and result.

## Boundaries

### B-1 · it simulates money movement, it does not move real money

- **Statement:** The product simulates holding and releasing COD money. It does not move real money.
- **Status:** confirmed
- **Why:** Moving real money needs a payment-intermediary license, which is outside the nature of this practice system.
- **Spec implications:** The wallet extension records money movement and never calls a real payment rail. No use case transfers real funds.

### B-2 · it is not a sales or marketplace suite

- **Statement:** The product does not sell goods and does not integrate marketplaces that deliver and pay out on their own.
- **Status:** confirmed
- **Why:** A marketplace runs a different reconciliation process; the product reconciles carrier COD by its nature.
- **Spec implications:** No use case creates a sale or reads a marketplace order. The product's input is a shop's own carrier orders.

### B-3 · it is not the shop's warehouse or accounting system

- **Statement:** The product does not keep inventory and does not do accounting or tax. It confirms that returned goods came back, and it exports data for a later accounting step.
- **Status:** confirmed
- **Why:** Reconciliation only needs to know a return arrived; a ledger of record for accounting is a different product.
- **Spec implications:** Return handling records only whether a return arrived. Accounting is served by a data export, not by a use case inside the product.
